# План внедрения дизайна Stitch в Mailing Agent

Ветка: `new-design`

## Цель

Встроить редактор шаблонов из Google Stitch в существующий Mailing Agent как часть рабочего процесса рассылки. Не создавать отдельный параллельный продукт и не дублировать уже работающие загрузку данных, генерацию документов, проверку текста, отправку и статистику.

## Основной принцип интеграции

Редактор шаблонов становится самостоятельным продуктовым разделом **«Шаблоны»**, а конкретная рассылка выбирает активные версии шаблонов и использует их в текущем пайплайне:

`Шаблоны → Рассылка → Аудитория → Документы → Отправка → Результаты`

## Этап 1. Карта соответствия и gap-анализ

Сопоставить каждый макет Stitch с существующими возможностями сервиса.

| Макет Stitch | Что уже есть | Что нужно добавить |
| --- | --- | --- |
| Загрузка и AI-генерация | Загрузка шаблонов, анализ КП, тестовая генерация | Единый стартовый экран, библиотека, понятные состояния загрузки |
| Редактор КП | Подстановка полей, адаптивные версии, генерация PDF | Визуальное редактирование, панель свойств, сохранение черновика |
| Редактор письма | TXT/DOCX-шаблон письма и переменные | Визуальный редактор блоков, кнопок и подписи |
| Динамические поля и AI | Технические placeholders и AI-обработка документов | Явная модель происхождения значения, AI-инструкция и ручные изменения |
| Выбор поля внешнего сервиса | Поля `data.xlsx` и данные парсера | Унифицированный каталог источников и интерфейс mapping |
| Сравнение и обновление данных | Повторная генерация и состояния job | Diff исходного, нового и вручную изменённого значения |
| Предпросмотр и проверка | Template preview, PDF preview, сертификация | Единый экран проверки с ошибками, предупреждениями и подтверждением |
| Design System | Частично существующие CSS-компоненты | Токены, состояния компонентов и адаптивные правила |

Результат этапа: список функций `используем как есть / адаптируем / разрабатываем` с привязкой к файлам и API.

## Этап 2. Информационная архитектура

Добавить верхнеуровневый раздел **«Шаблоны»**:

1. Библиотека шаблонов.
2. Создание и загрузка.
3. Редактор.
4. Динамические поля.
5. Предпросмотр и проверка.
6. История версий и активация.

В настройках рассылки вместо повторной загрузки файлов пользователь выбирает активные шаблоны из библиотеки. Быстрая загрузка внутри рассылки может остаться как сокращённый путь.

## Этап 3. Дизайн-система

Перенести из Stitch:

- зелёную палитру Material Design 3;
- типографику и иерархию заголовков;
- сетку редактора: библиотека, холст, свойства;
- кнопки, поля, tabs, chips, badges, toolbars;
- состояния `hover`, `focus`, `disabled`, `loading`, `success`, `warning`, `error`;
- desktop/tablet/mobile-поведение.

Оформить значения как CSS custom properties. Новые компоненты не должны зависеть от inline-стилей из текущего `index.html`.

## Этап 4. Модель данных и API

До реализации редактора определить контракты:

- `Template` — письмо, КП или договор;
- `TemplateVersion` — черновик, проверенная или активная версия;
- `TemplateField` — техническое имя, тип и формат;
- `FieldSource` — сервис, сущность и путь к полю;
- `AiFieldConfig` — исходные поля, инструкция, стиль, длина и ограничения;
- `FieldValueState` — из сервиса, создано AI, вручную, изменено вручную, нет данных, требует проверки;
- `TemplateValidation` — проверки, ошибки, предупреждения и артефакты preview.

Сначала переиспользовать существующие adaptive-template endpoints. Новые API добавлять только для функций, которых в текущем backend действительно нет.

## Этап 5. Каркас редактора

Реализовать вертикальными срезами:

1. Библиотека и выбор типа шаблона.
2. Загрузка файла и создание версии.
3. Центральный холст и базовое редактирование.
4. Правая панель свойств выбранного элемента.
5. Сохранение черновика и восстановление состояния.

Каждый срез должен быть подключён к реальным данным до перехода к следующему.

## Этап 6. Динамические поля

Добавить три режима заполнения:

1. Данные из сервиса.
2. Сформировать с помощью AI.
3. Ввести вручную.

Для каждого поля показывать происхождение значения и наличие ручных изменений. Автоматическое обновление не должно затирать ручную правку без явного решения пользователя.

## Этап 7. Предпросмотр, проверка и версии

Объединить существующие анализ, тестовую генерацию и сертификацию в один сценарий:

1. Проверить найденные поля.
2. Подставить тестовые данные.
3. Сформировать пример.
4. Показать PDF и список проблем.
5. Исправить или подтвердить.
6. Активировать прошедшую проверку версию.

Неуспешная версия не заменяет текущую активную.

## Этап 8. Интеграция с рассылкой

- настройки рассылки сохраняют ссылки на версии шаблонов;
- генератор использует зафиксированную версию на протяжении всего запуска;
- изменение активного шаблона не меняет уже запущенную рассылку;
- в истории рассылки видны использованные версии;
- терминология унифицируется: «рассылка», «организация», «шаблон», «версия».

## Этап 9. Проверка качества

Обязательные сценарии:

- создать шаблон из DOCX/PDF/TXT;
- открыть существующую версию;
- настроить прямое динамическое поле;
- настроить AI-поле;
- изменить автоматически заполненное значение вручную;
- увидеть diff после обновления источника;
- сформировать и проверить пример;
- активировать версию;
- выбрать её в рассылке;
- пройти генерацию документов без регрессий;
- проверить пустые, ошибочные, остановленные и повторные состояния;
- проверить клавиатурную навигацию и основные responsive-breakpoints.

## Порядок поставки

### MVP

Библиотека → загрузка → существующие placeholders → preview → сертификация → активация → выбор в рассылке.

### Следующая версия

Визуальное редактирование письма и документов, каталог источников, статусы происхождения значений.

### Расширенная версия

AI-поля, сравнение обновлений, Code Connect/Figma-процесс и полноценная совместная работа над шаблонами.

## Критерии готовности

- новый редактор не дублирует существующий пайплайн;
- текущие рассылки продолжают работать со старыми шаблонами;
- пользователь всегда понимает, какая версия активна;
- автоматически полученные значения не затирают ручные изменения молча;
- preview соответствует файлам, которые получат адресаты;
- новая навигация не содержит одновременно старую и новую статистику;
- все новые состояния покрыты тестами и макетами.
